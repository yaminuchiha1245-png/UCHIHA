# Client Services Store

نسخة متجر تيليجرام مستقلة للعميل، مبنية فوق محرك UCHIHA Store مع عزل الكتالوج والأسرار والدفع عن المتجر الأصلي.

الفرع الحالي:

```text
client/ios-android-services-store-v1
```

فرع `main` لا يتم تعديله بواسطة نسخة العميل.

## واجهة العميل

القائمة الرئيسية:

- 📱 منتجات iOS
- 🤖 منتجات Android
- 💎 Diamond FF
- 💳 شحن رصيد
- 👤 حسابي
- 📦 طلباتي
- 📞 الدعم

منتجات iOS:

- 📜 الشهادات
- 📂 الملفات
- 🌐 البروكسي
- 🖥️ البنلات

منتجات Android:

- 🖥️ البنلات
- 📂 الملفات
- 🌐 البروكسي

رتب الحساب:

- ⭐ عميل
- 👑 موزع

الموزع يمكن أن يحصل على خصم افتراضي، خصم خاص بحسابه، أو سعر موزع ثابت لمنتج معين.

## Runtime العميل

التشغيل الرسمي للنسخة هو:

```bash
python client_store_launcher.py
```

`client_store_launcher.py` لا يستخدم `storefront_launcher.py` إطلاقًا.

هذا مقصود لأن `storefront_launcher.py` الخاص بالمتجر الأصلي يثبت تكاملات JS4Card وBinance وShamCash وWeb Store. نسخة العميل تعمل Telegram-only فوق `bot.main()` ثم تثبت وحدات العميل الخاصة بها فقط.

قبل استيراد `bot.py` يقوم الـLauncher بعزل البيئة:

- يمسح `API_TOKEN` القديم من بيئة العملية.
- يمسح مفاتيح Binance القديمة.
- يمسح TronGrid key القديم.
- يمسح ShamCash API token القديم.
- يجبر مزامنة JS4Card القديمة على التوقف.
- يجبر Binance/ShamCash API القديمين على التوقف.
- يعطل Storefront Web/API القديم.
- يعطل مراقب طلبات JS4Card القديم.

`BOT_TOKEN` و`ADMIN_ID` وإعدادات `CLIENT_*` الخاصة بالعميل لا يتم مسحها.

## إعداد أول تشغيل

بعد تثبيت الاعتمادات:

```bash
pip install -r requirements.txt
python client_setup.py
```

صاحب البوت هو من يدخل:

- Telegram BOT_TOKEN
- Telegram ADMIN_ID
- اسم متجره
- مسار قاعدة البيانات إن أراد تغييره

`client_setup.py` ينشئ `.env` جديدًا من قائمة مسموح بها بدل نسخ بيئة UCHIHA القديمة.

مهم: BOT_TOKEN يحتاج Bootstrap قبل أن يستطيع البوت الاتصال بتيليجرام، لذلك يُدخل في إعداد أول التشغيل. أما توكنات مزودي المنتجات فتدخل من داخل لوحة البوت بعد تشغيله ولا يحتاج المبرمج إلى معرفتها.

## هوية العميل

اسم المتجر ملك لصاحب النسخة:

- يحدد في أول تشغيل.
- يظهر عند `/start`.
- يمكن تغييره من `🧰 إدارة متجر العميل → 🏷️ هوية المتجر`.
- رسالة واتساب في الدعم تستخدم اسم متجر العميل الحالي.
- رسالة الدعم الافتراضية لا تحتوي اسم UCHIHA STORE.

كل ما يخص كتالوج العميل موجود داخل:

`🧰 إدارة متجر العميل`

وتحتوي على:

## شحن الرصيد وطرق الدفع

نسخة العميل تعتمد افتراضيًا على طرق دفع يدوية يضيفها صاحب البوت من:

`لوحة الإدارة → 💸 طرق الدفع`

المحرر يسمح بتحديد:

- اسم طريقة الدفع.
- بيانات/حساب التحويل.
- العملة.
- الحد الأدنى والأعلى.
- معدل إضافة الرصيد والرسوم الموجودة في المحرك الأصلي.
- طريقة إثبات الدفع: صورة إيصال أو رقم عملية أو كلاهما.
- التفعيل/التعطيل والترتيب.

الطريقة اليدوية تحفظ كـ`provider=local` و`payment_mode=manual`.

### عزل الدفع القديم

نسخة العميل لا تستخدم مفاتيح Binance/ShamCash من `.env`.

حتى لو استُخدمت قاعدة بيانات قديمة تحتوي طرق Binance/ShamCash/JS4Card:

- يتم تعطيل الطرق غير المحلية تلقائيًا عند إقلاع نسخة العميل.
- لا يتم حذف البيانات القديمة.
- لا تظهر هذه الطرق ضمن شاشة إدارة الدفع الخاصة بالعميل.
- callbacks الخاصة بـBinance/ShamCash القديمة محجوبة في Runtime العميل.

إذا احتاج العميل لاحقًا دفعًا آليًا، يجب إضافته كتکامل عميل مستقل بأسراره المشفرة من لوحة الإدارة، وليس بإعادة استخدام أسرار UCHIHA القديمة.

## إدارة الموزعين

من `🧰 إدارة متجر العميل → 👑 إعدادات الموزعين`:

- قائمة الموزعين.
- أحدث العملاء.
- البحث بـTelegram ID أو @username أو الاسم.
- ترقية عميل إلى موزع.
- إعادة موزع إلى عميل.
- خصم خاص للحساب.
- الرجوع للخصم الافتراضي.
- تعديل الخصم الافتراضي للموزعين.

## إدارة مزودي API

من:

`🧰 إدارة متجر العميل → 🔌 مزودو API`

صاحب البوت يستطيع:

- إضافة مزوّد.
- إدخال Base URL.
- إدخال Catalog endpoint.
- إدخال/تبديل API Token.
- اختيار Bearer أو X-API-Key أو Query Parameter أو Auto أو بدون مصادقة.
- تفعيل/إيقاف المزوّد.
- مزامنة الكتالوج.

التوكن:

- يدخل من صاحب البوت داخل Telegram.
- تشفره Fernet قبل التخزين.
- لا يظهر كاملًا بعد الحفظ.
- تحذف رسالة تبديل التوكن قدر الإمكان بعد قراءتها.
- يستخدم التشفير وفك التشفير نفس `CLIENT_STORE_MASTER_KEY_FILE` أو `CLIENT_STORE_MASTER_KEY`.

HTTPS مطلوب افتراضيًا لمزودي API.

## ترتيب المنتجات

المنتج الجديد من API يدخل إلى:

`📥 غير مرتبة`

ثم يحدد صاحب البوت:

- iOS / Android / Diamond FF.
- القسم الفرعي إن وجد.
- سعر البيع.
- سعر الموزع الاختياري.
- الترتيب.
- التفعيل/التعطيل.
- متطلب الطلب إن وجد.

بعد الاعتماد يصبح ضمن المنتجات المرتبة ويظهر للعميل.

المزامنة اللاحقة تحدث اسم المنتج وتكلفة المزوّد والـJSON الخام، لكنها تحافظ على مكان المنتج وسعر البيع الذي حدده صاحب البوت.

## المنتجات اليدوية

من:

`🧰 إدارة متجر العميل → ➕ إضافة منتج يدوي`

يمكن إنشاء خدمة بدون API. بعد الاسم والسعر وتعليمات التسليم تدخل إلى «غير مرتبة» لتحديد مكانها.

الشراء اليدوي:

- يفحص الرصيد.
- يخصم داخل معاملة SQLite.
- ينشئ طلبًا.
- يسجل حركة الرصيد.
- يرسل إشعارًا للإدارة.

## متطلبات الطلب

لكل منتج يمكن تحديد معلومة يجب أن يرسلها العميل قبل التأكيد، مثل:

- Player ID لـDiamond FF.
- UDID للشهادة.
- رقم حساب أو اسم مستخدم حسب الخدمة.

لن يتم الخصم قبل إرسال المعلومة المطلوبة ثم الضغط على التأكيد.

## شراء منتجات API

الشراء الخارجي متوقف افتراضيًا لكل مزوّد.

من:

`🧰 إدارة متجر العميل → 🔁 إعداد شراء API`

يمكن ضبط، حسب توثيق المزوّد:

- Purchase endpoint.
- POST / PUT / PATCH / GET.
- JSON / Form / Query.
- اسم Product ID field.
- اسم Customer Input field.
- Quantity field.
- مسار Order ID داخل JSON.
- مسار Status داخل JSON.
- حالات القبول والإكمال والفشل.

أي تعديل حساس في إعداد الشراء يعطل الشراء حتى يراجعه المالك ويعيد تفعيله.

يتم إرسال `Idempotency-Key` لتقليل خطر التكرار عندما يدعمه المزوّد.

### سياسة الاسترجاع

- رفض مؤكد/4xx/حالة فشل صريحة: Refund مرة واحدة.
- Timeout أو انقطاع شبكة أو 5xx: لا Refund تلقائي ولا إعادة إرسال تلقائي.
- النتيجة غير المؤكدة تصبح `⚠️ يحتاج تحقق` وتصل للإدارة.

هذا يمنع حصول العميل على الخدمة ثم استرجاع الرصيد بسبب انقطاع الرد.

## متابعة طلبات API

إذا وفر المزوّد Status endpoint رسميًا يمكن ضبطه من:

`🧰 إدارة متجر العميل → 📡 متابعة طلبات API`

يدعم مسارًا مثل:

```text
/orders/{order_id}
```

أو query parameter للـorder ID، مع Status key مثل `status` أو `data.status`.

المراقب لا يتصل بأي مزوّد ما لم يفعّل المالك Status endpoint له.

- Completed يغلق الطلب.
- Failed/Rejected الصريح يعمل Refund مرة واحدة.
- الحالة المجهولة لا تعيد الرصيد تلقائيًا.

## حساب العميل وطلباته

«حسابي» يعرض:

- الاسم والمعرف.
- رقم الحساب.
- ⭐ عميل / 👑 موزع.
- خصم الموزع الفعلي.
- الرصيد.
- عدد الطلبات والمكتملة والمفتوحة.

«طلباتي» تميز:

- 📝 طلب يدوي.
- 🔌 طلب API.
- ✅ مكتمل.
- 🔄 قيد المعالجة.
- ↩️ مسترجع.
- ⚠️ يحتاج تحقق.

ويظهر رقم طلب المزوّد عندما يكون متاحًا.

## فحص الجاهزية

```bash
python client_readiness.py
```

الفحص لا يطبع أسرارًا، ويتحقق من:

- BOT_TOKEN شكليًا بدون عرضه.
- ADMIN_ID.
- مفتاح Fernet.
- قاعدة البيانات.
- وجود أسرار UCHIHA/الدفع القديمة في البيئة كتنبيه فقط؛ Launcher العميل يتجاهلها.
- الجداول الأساسية.
- إعدادات مزودي API.
- شراء/متابعة API المفعّلة دون endpoint.
- المنتجات غير المرتبة.
- وجود طريقة شحن يدوية محلية.
- وجود طرق دفع قديمة سيقوم Runtime بعزلها.

## CI

`.github/workflows/client-store-check.yml` يشغّل:

- Python 3.12.
- تثبيت `requirements.txt`.
- التحقق أن `.env` ومفتاح العميل والبيانات المحلية ليست tracked.
- `py_compile` للوحدات الجديدة.
- Import checks.
- `unittest discover` لكل `test_client_*.py`.
- اختبارات التشفير/فك التشفير.
- اختبارات التسعير والموزعين.
- اختبارات شراء API والاسترجاع.
- اختبارات Status API.
- اختبارات عزل الدفع.
- Smoke Test يثبت Runtime العميل كاملًا على قاعدة جديدة ويتأكد أن storefront/Binance/ShamCash Admin غير محملة.

نجاح CI لا يثبت API خارجيًا حقيقيًا قبل إدخال بيانات المزوّد الفعلي؛ لكنه يثبت منطق النسخة المحلية والعزل ومسارات الأمان التي يمكن اختبارها بدون أسرار العميل.
