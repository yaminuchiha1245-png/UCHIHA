# Client Services Store

هذه النسخة مخصّصة لعميل مستقل ومبنية فوق UCHIHA Store بدون تعديل فرع `main`.
مصدر العمل الحالي هو الفرع:

```text
client/ios-android-services-store-v1
```

## واجهة العميل

القائمة الرئيسية:

- 📱 منتجات iOS
- 🤖 منتجات Android
- 💎 Diamond FF
- 💳 شحن رصيد
- 👤 حسابي

منتجات iOS:

- 📜 الشهادات
- 📂 الملفات
- 🌐 البروكسي
- 🖥️ البنلات

منتجات Android:

- 🖥️ البنلات
- 📂 الملفات
- 🌐 البروكسي

الحساب يدعم رتبتين:

- ⭐ عميل
- 👑 موزع

يمكن للموزع الحصول على نسبة خصم عامة أو خصم خاص بحسابه أو سعر موزع ثابت لمنتج محدد.

واجهة «حسابي» تعرض الرتبة والخصم الفعلي والرصيد وإحصاءات الطلبات. شاشة «طلباتي» تميّز بين الطلب اليدوي وطلب API وتعرض الحالات المكتملة والمسترجعة وغير المؤكدة بوضوح.

## هوية العميل

اسم المتجر ملك لصاحب النسخة ولا يعتمد على اسم UCHIHA الظاهر للمستخدم.

- يحدد صاحب البوت الاسم أثناء `client_setup.py`.
- يظهر الاسم عند `/start`.
- يمكن تغييره لاحقًا من `🧰 إدارة متجر العميل → 🏷️ هوية المتجر`.
- deep-link `/start payload` يبقى للمحرك الأصلي ولا يتم كسره.

## إعداد أول تشغيل

بعد تثبيت الاعتمادات:

```bash
pip install -r requirements.txt
python client_setup.py
```

صاحب البوت هو من يدخل:

- Telegram BOT_TOKEN
- Telegram ADMIN_ID
- اسم متجره
- مسار قاعدة البيانات إن أراد تغييره

ينشئ الإعداد ملف `.env` جديدًا من قائمة مسموح بها ولا ينسخ أسرار UCHIHA القديمة مثل `API_TOKEN` أو مفاتيح Binance/TronGrid.

لا يتم إدخال توكنات مزودي المنتجات في هذا الإعداد. تُضاف من داخل لوحة إدارة البوت بعد تشغيله.

لتشغيل نسخة العميل:

```bash
python client_store_launcher.py
```

## لوحة الإدارة

اللوحة العامة تحتفظ بالأجزاء المفيدة من UCHIHA مثل:

- المستخدمون
- الطلبات
- الرصيد
- الدفع والشحن
- الدعم
- الإعدادات
- سجل العمليات والإحصائيات حسب الصلاحية

أما كل ما يخص كتالوج العميل فمجمّع داخل:

`🧰 إدارة متجر العميل`

وتحتوي على:

- 🏷️ هوية المتجر
- ➕ إضافة منتج يدوي
- 📥 غير مرتبة
- ✅ المنتجات المرتبة
- 🔎 بحث المنتجات
- 🧾 متطلبات الطلب
- 🔌 مزودو API
- 🔄 مزامنة API
- 🔁 إعداد شراء API
- 📡 متابعة طلبات API
- 👑 إدارة الموزعين
- 📊 ملخص الكتالوج

أزرار المنتجات والأقسام ومزامنة JS4Card القديمة لا تظهر في لوحة نسخة العميل حتى لا توجد لوحتان متعارضتان.

## إدارة الموزعين

من `🧰 إدارة متجر العميل → 👑 إعدادات الموزعين` يمكن لصاحب البوت:

- مشاهدة قائمة الموزعين.
- مشاهدة أحدث العملاء.
- البحث بـ Telegram ID أو @username أو الاسم.
- ترقية العميل إلى موزع أو إعادته إلى عميل.
- وضع خصم خاص لموزع محدد.
- إعادة الحساب لاستخدام الخصم الافتراضي.
- تعديل الخصم الافتراضي لجميع الموزعين.

## إدارة مزودي API

من:

`🧰 إدارة متجر العميل → 🔌 مزودو API`

يمكن لصاحب البوت:

- إضافة مزوّد جديد.
- إدخال Base URL ومسار الكتالوج.
- إدخال أو تبديل API Token.
- اختيار طريقة المصادقة: Bearer أو X-API-Key أو Query Parameter أو تلقائي أو بدون مصادقة.
- تفعيل/إيقاف المزوّد.
- تشغيل مزامنة الكتالوج يدويًا.

توكن المزوّد يُشفّر باستخدام Fernet ولا يُعرض كاملًا بعد حفظه. رسالة تبديل التوكن تحذف من المحادثة قدر الإمكان بعد قراءتها.

روابط API تستخدم HTTPS افتراضيًا.

## ترتيب المنتجات

منتجات API الجديدة تدخل إلى:

`📥 غير مرتبة`

صاحب البوت يحدد مكان المنتج ثم يعتمده. بعد الاعتماد ينتقل إلى:

`✅ تم ترتيبها`

يمكن تحديد:

- iOS / Android / Diamond FF.
- القسم الفرعي عند الحاجة.
- سعر البيع.
- سعر الموزع الاختياري.
- رقم الترتيب.
- تفعيل أو تعطيل المنتج.
- متطلب العميل مثل Player ID أو UDID.

المزامنة اللاحقة تحدث تكلفة المزوّد والبيانات الخام، لكنها تحافظ على سعر البيع ومكان المنتج الذي رتبه صاحب البوت.

## المنتجات اليدوية

يمكن إنشاء منتج يدوي بدون أي API من:

`🧰 إدارة متجر العميل → ➕ إضافة منتج يدوي`

بعد إدخال الاسم والسعر وتعليمات التسليم، يدخل المنتج إلى `📥 غير مرتبة` ليتم وضعه في القسم الصحيح.

الشراء اليدوي يعمل من رصيد العميل داخل معاملة قاعدة بيانات، ينشئ طلبًا ويضيف سجل خصم ويرسل إشعارًا لصاحب البوت.

يمكن تحديد متطلب للطلب قبل الخصم، مثل:

- ID اللاعب لشحن Diamond FF.
- UDID للشهادات.
- اسم حساب أو رقم يطلبه صاحب الخدمة.

## شراء منتجات API

المزوّد العام لا يُسمح له بالشراء تلقائيًا بمجرد إضافة التوكن. الشراء يكون متوقفًا افتراضيًا.

من:

`🧰 إدارة متجر العميل → 🔁 إعداد شراء API`

يمكن لصاحب البوت، حسب توثيق المزوّد، تحديد:

- Purchase endpoint.
- HTTP Method: POST / PUT / PATCH / GET.
- إرسال البيانات كـ JSON أو Form أو Query.
- اسم حقل Product ID.
- اسم حقل بيانات العميل.
- اسم حقل Quantity.
- مسار رقم الطلب داخل استجابة JSON.
- مسار Status داخل استجابة JSON.
- الحالات المقبولة والمكتملة والفاشلة.

أي تعديل حساس في إعداد الشراء يوقف الشراء تلقائيًا حتى يراجعه المالك ويعيد تفعيله.

طلبات الشراء تستخدم `Idempotency-Key` لتقليل خطر التكرار عندما يدعم المزوّد هذا الرأس.

### سياسة الاسترجاع الآمنة

- رفض صريح/4xx/حالة `failed` أو `rejected` المعرّفة: يرجع الرصيد مرة واحدة فقط.
- Timeout أو انقطاع شبكة أو 5xx: لا يرجع الرصيد تلقائيًا ولا يعاد إرسال الطلب تلقائيًا، لأن المزوّد قد يكون نفّذ الطلب قبل انقطاع الرد.
- النتيجة غير المؤكدة تصبح `⚠️ يحتاج تحقق` وتصل رسالة للإدارة.

هذا يمنع حالة حصول العميل على الخدمة من المزوّد ثم استرجاع الرصيد بالخطأ.

## متابعة حالات API

إذا كان المزوّد يقدم endpoint رسميًا للاستعلام عن حالة الطلب، يمكن إعداده من:

`🧰 إدارة متجر العميل → 📡 متابعة طلبات API`

يدعم:

- مسار مثل `/orders/{order_id}`.
- أو endpoint يستخدم `?order_id=...`.
- Status key مثل `status` أو `data.status`.
- فحص يدوي من لوحة الإدارة.
- مراقب خفيف افتراضي كل 120 ثانية.

لا يرسل المراقب أي HTTP request إلى مزوّد إلا إذا فعّل صاحب البوت Status endpoint لذلك المزوّد.

الحالة المكتملة تغلق الطلب، والحالة الفاشلة الصريحة تعمل Refund مرة واحدة، والحالة المجهولة تبقى بدون استرجاع تلقائي.

## فحص الجاهزية

بعد الإعداد أو قبل التسليم يمكن تشغيل:

```bash
python client_readiness.py
```

يفحص بدون طباعة الأسرار:

- شكل BOT_TOKEN بدون عرضه.
- ADMIN_ID.
- وجود وصحة مفتاح Fernet.
- مسار قاعدة البيانات.
- عدم وجود أسرار UCHIHA القديمة غير المطلوبة.
- الجداول الأساسية.
- إعدادات مزودي API المفعّلين.
- شراء/متابعة API المفعّلة بدون مسارات.
- المنتجات الموجودة في «غير مرتبة».

## الأمان والعزل

- متجر UCHIHA الأصلي على `main` لا يتم تعديله.
- نسخة العميل تعمل من Launcher مستقل.
- مزامنة JS4Card القديمة معطلة افتراضيًا في نسخة العميل.
- Storefront Web/API القديمة معطلة افتراضيًا في نسخة العميل.
- Binance auto payment معطل افتراضيًا.
- روابط مزودي API يجب أن تكون HTTPS افتراضيًا.
- `.env` وقواعد البيانات ومفتاح `client_store.key` مستثناة من Git.
- مفتاح تشفير المزودين يجب أن يبقى مع قاعدة بيانات العميل والنسخ الاحتياطية الآمنة.
- صلاحيات المشرفين تحدد من يستطيع إدارة المستخدمين أو المنتجات أو المزامنة أو الطلبات.

## CI

GitHub Actions يشغّل على Python 3.12:

- تثبيت `requirements.txt`.
- التحقق أن أسرار العميل الأساسية غير متتبعة في Git.
- `py_compile` لوحدات نسخة العميل.
- استيراد الوحدات.
- جميع اختبارات `test_client_*.py`.

الاختبارات تغطي، من ضمن ما تغطيه:

- تشفير/فك توكنات المزودين.
- قراءة كتالوج JSON.
- طرق المصادقة.
- أسعار الموزعين.
- متطلبات الطلب.
- تنظيف لوحة الإدارة.
- إعداد شراء API.
- الاسترجاع مرة واحدة.
- عدم الاسترجاع في الحالة غير المؤكدة.
- انتقال حالة API إلى مكتمل أو مسترجع.
- عزل أسرار أول تشغيل.
- هوية المتجر وشارات الطلبات.

نجاح CI لا يثبت أن مزوّدًا خارجيًا بعينه يعمل قبل إدخال إعداداته وفق توثيقه وإجراء طلب حقيقي بإشراف صاحب حساب المزوّد.
