# نشر وتسليم نسخة متجر العميل

هذا الدليل خاص بالفرع:

```text
client/ios-android-services-store-v1
```

ولا يحتاج أي توكن مزوّد API أثناء النشر.

## 1. متطلبات السيرفر

- Linux VPS.
- Python 3.12 أو أحدث.
- مستخدم خدمة مستقل، مثال `clientstore`.
- مجلد تطبيق مستقل، مثال `/opt/client-store`.
- اتصال HTTPS خارجي للوصول إلى APIs التي يضيفها صاحب البوت.

يفضّل ألا تعمل نسخة العميل تحت root.

## 2. تجهيز التطبيق

داخل مجلد المشروع:

```bash
python3.12 -m venv .venv
.venv/bin/pip install --upgrade pip
.venv/bin/pip install -r requirements.txt
```

## 3. صاحب البوت يدخل بياناته بنفسه

يشغّل المالك:

```bash
.venv/bin/python client_setup.py
```

ويُطلب منه:

- Telegram BOT_TOKEN.
- Telegram ADMIN_ID.
- اسم المتجر.
- مسار قاعدة البيانات إن أراد تغييره.

`client_setup.py` ينشئ `.env` محليًا بصلاحيات مقيدة وينشئ مفتاح Fernet محليًا.

توكنات مزودي المنتجات **لا** تدخل في هذا الإعداد؛ يضيفها المالك من لوحة إدارة البوت بعد التشغيل.

## 4. فحص ما قبل التشغيل

```bash
.venv/bin/python client_readiness.py
```

لا يطبع هذا الفحص BOT_TOKEN أو API tokens أو مفتاح Fernet.

يجب معالجة أي `FAIL` قبل اعتماد النسخة. التنبيهات `WARN` قد تكون طبيعية مثل عدم إضافة مزوّد API أو طريقة دفع بعد.

## 5. تشغيل يدوي أول مرة

```bash
.venv/bin/python client_store_launcher.py
```

ثم يختبر المالك في Telegram:

1. `/start` ويظهر اسم متجره.
2. فتح `⚙️ لوحة الإدارة`.
3. إضافة طريقة شحن يدوية من `💸 طرق الدفع`.
4. إضافة منتج يدوي تجريبي أو مزوّد API.
5. ترتيب المنتج داخل iOS / Android / Diamond FF.
6. التأكد أن المنتج بسعر أكبر من صفر.
7. تجربة حساب عميل عادي وحساب موزع عند الحاجة.

## 6. تشغيل systemd

يوجد نموذج بلا أسرار:

```text
deploy/client-store.service.example
```

عدّل فقط:

- `User` و`Group`.
- `WorkingDirectory`.
- مسار `.env`.
- مسار Python داخل `.venv`.

ثم ضع الملف باسم مناسب داخل `/etc/systemd/system/` وشغّل الخدمة وفق إدارة النظام المعتادة.

لا تضع BOT_TOKEN أو أي API Token داخل ملف service نفسه.

## 7. النسخ الاحتياطية

Runtime العميل ينشئ نسخ SQLite محلية افتراضيًا كل 6 ساعات ويحتفظ بآخر 7 نسخ.

من لوحة الإدارة:

`🧰 إدارة متجر العميل → 🗄 النسخ الاحتياطية`

يمكن للمالك:

- إنشاء نسخة الآن.
- فحص سلامة آخر نسخة.

كل Snapshot يتضمن:

- نسخة متسقة من SQLite.
- مفتاح Fernet إن كان موجودًا.
- `manifest.json` مع SHA-256 لقاعدة البيانات.

الفحص يتحقق من:

- تطابق SHA-256.
- `PRAGMA integrity_check` لقاعدة SQLite.
- صحة مفتاح Fernet عندما يتوقعه manifest.

لا يوجد زر Restore مباشر داخل Telegram؛ هذا مقصود لتفادي استبدال قاعدة الإنتاج بضغطة خاطئة. الاستعادة عملية صيانة يتم تنفيذها بعد إيقاف الخدمة والتحقق من Snapshot المطلوب.

## 8. سياسة الدفع

نسخة العميل لا تحمل تلقائيًا Binance/ShamCash/JS4Card من UCHIHA القديم.

طرق الشحن الافتراضية هي الطرق اليدوية التي ينشئها صاحب المتجر من لوحة البوت، ويمكن أن تطلب صورة إيصال أو رقم عملية وفق الإعداد.

إذا كانت قاعدة البيانات من نسخة أقدم وتحتوي طرق دفع غير محلية، يتم تعطيلها عند إقلاع Runtime العميل دون حذف بياناتها.

## 9. مزودو API

المالك يضيف من:

`🧰 إدارة متجر العميل → 🔌 مزودو API`

ثم يحدد:

- HTTPS Base URL.
- Catalog endpoint.
- API token/key.
- طريقة المصادقة.

بعد المزامنة تدخل المنتجات الجديدة إلى `📥 غير مرتبة`.

الشراء الخارجي لا يتفعل تلقائيًا عند إضافة المزوّد. يجب إعداد Purchase endpoint ومراجعة الحقول ثم تفعيل الشراء صراحة.

## 10. حماية الطلبات

- المنتج بدون سعر صالح لا يعتمد للعرض.
- الطلب اليدوي يُخصم مرة واحدة داخل معاملة قاعدة بيانات.
- إلغاء طلب يدوي مدفوع من الإدارة يعيد الرصيد مرة واحدة.
- الطلب اليدوي المكتمل لا يقبل الإلغاء السريع بعد التسليم.
- طلب API لا يُلغى من زر الحالة العام؛ تتم متابعته عبر مركز API لتفادي استرجاع رصيد لطلب قد يكون المزوّد نفذه.
- Timeout/5xx لشراء API لا يعني فشلًا مؤكدًا، لذلك لا يحدث Refund تلقائي.

## 11. ما لا يتم تسليمه داخل Git

يجب أن تبقى محلية فقط:

- `.env`
- `client_store.key`
- `*.db`, `*.db-wal`, `*.db-shm`
- `.backups/`
- أي session/log يحتوي بيانات تشغيلية

## 12. فحص الكود

GitHub Actions على فرع العميل يختبر:

- Python 3.12.
- تثبيت الاعتمادات.
- عدم تتبع الأسرار والنسخ الاحتياطية.
- Compile وImport للوحدات.
- اختبارات API والتشفير والتسعير والموزعين.
- شراء API واسترجاعه الآمن.
- متابعة الطلبات.
- عزل الدفع القديم.
- Backup/manifest/integrity/retention.
- منع السعر صفر.
- إلغاء الطلب اليدوي مع Refund مرة واحدة.
- Smoke Test للـRuntime المعزول كاملًا.

نجاح CI لا يثبت API خارجيًا بعينه؛ اختبار المزوّد الحقيقي يتم بعد أن يضيف المالك بياناته الرسمية من لوحة البوت.
