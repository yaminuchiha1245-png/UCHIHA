# سياسة الفروع في UCHIHA

## فروع المصدر المعتمدة

| المشروع | فرع المصدر | الاستخدام |
|---|---|---|
| UCHIHA Store | `main` | المتجر والبوت والتكاملات الحالية |
| UCHIHA Builder | `builder/v1-platform` | منصة uchiha-builder.com متعددة المستأجرين |
| UCHIHA Debt Store | `debt-store-build` | تطبيق الديون Android |

## قاعدة التسمية للفروع الجديدة

استخدم صيغة تربط الفرع بالمشروع والهدف:

- `store/feature-<name>`
- `store/fix-<name>`
- `builder/feature-<name>`
- `builder/fix-<name>`
- `debt/feature-<name>`
- `debt/fix-<name>`
- `release/<project>-<version>`
- `backup/<project>-YYYYMMDD`

لا نستخدم أسماء عامة لا توضّح المشروع.

## الفروع القديمة

الفروع التي تبدأ بـ`agent/` أو `codex/` أو `copilot/` تعتبر فروع عمل تاريخية/مؤقتة. لا تعتمد كمصدر حقيقة حتى لو كان اسمها يحتوي `final` أو `complete`.

قبل حذف أي فرع قديم:

1. قارن الفرع مع مصدر المشروع المعتمد.
2. تأكد أن كل Commit مهم موجود أو تم نقله.
3. احتفظ بنقطة Backup واحدة عند الحاجة.
4. بعدها يمكن حذف الفرع من GitHub.

## قواعد الدمج

- لا دمج مباشر بين `main` و`builder/v1-platform` لمجرد توحيد الشكل.
- لا تُنقل ملفات تطبيق الديون إلى `main` قبل وجود قرار معماري واضح.
- أي تغيير في الدفع أو الرصيد يحتاج اختبار منع التكرار قبل الدمج.
- أي تغيير Production في Builder يحتاج نجاح CI والـsmoke/audit gates.
- الأسرار تبقى خارج Git ولا تدخل في Commit أو Issue أو Log.

## معنى كلمة مكتمل

لا يكفي اسم فرع مثل `final` أو `complete`.

المشروع يُعتبر مكتملًا فقط عندما:

- يبني بنجاح.
- يمر باختباراته المطلوبة.
- ينجح في بيئته الحقيقية أو Staging المناسبة.
- لا توجد خطوة تشغيل يدوية خطيرة غير موثقة.
- يوجد مسار رجوع/نسخة احتياطية واضح عند تحديث الإنتاج.
