# معمارية UCHIHA RADIUS

## القرار المعماري

يعتمد الإصدار الأول مسارًا واحدًا واضحًا: تطبيق المزود وتطبيق المالك وTelegram يتصلون بـ API واحد، والـ API وحده يصل إلى البيانات والتكاملات. لا تصل الواجهات مباشرة إلى MikroTik أو قاعدة البيانات.

```text
Provider PWA ─┐
Owner PWA ────┼── HTTPS API ── PostgreSQL
Telegram ─────┘       │
                      ├── RADIUS accounting connector
                      ├── MikroTik/agent command outbox
                      └── audit + alert outbox
```

## نطاق الإصدار الأول

1. تسجيل دخول Google وجلسات قابلة للإبطال.
2. مستأجرون وأعضاء بأدوار: owner، admin، operator، collector، viewer.
3. بوابة اشتراك: القراءة متاحة بعد الدخول، والكتابة/الربط/التنفيذ تتطلب اشتراكًا فعالًا.
4. مشتركون، باقات، جلسات، فواتير، دفعات، أجهزة وتنبيهات.
5. RADIUS Accounting موقّع وقابل لإعادة المحاولة بلا تكرار.
6. إعداد MikroTik عبر API أو VPN أو UCHIHA Agent مع أسرار مشفرة.
7. Telegram للتنبيهات والأوامر البسيطة للقراءة.
8. لوحة مالك منفصلة لإدارة المستأجرين والاشتراكات وسجل التدقيق.

## البيانات

SQLite مستخدم فقط للتطوير والاختبارات السريعة. النشر العام يستخدم PostgreSQL 16+ والمهاجر الموجود في `infra/postgres/migrations/001_initial.sql`. سياسات RLS دفاع إضافي؛ التطبيق يمرر المستأجر من جلسة موثوقة أيضًا.

## حدود الثقة

- Google يثبت هوية المستخدم، لكن العضوية والدور والاشتراك يقررها الخادم.
- لا يُقبل `tenant_id` من العميل لعمليات المزود.
- الأسرار لا تعاد إلى الواجهة بعد حفظها.
- أي أمر فصل أو تعليق أو تعديل مالي يكتب سجل تدقيق قبل إرجاع النجاح.
- Telegram لا ينفذ أوامر حساسة في الإصدار الأول.

## قابلية التوسع

المهام الخارجية تُسجل في outbox؛ العامل المنفصل يرسل Telegram وأوامر الشبكة. هذا يفصل زمن استجابة الزر عن بطء الشبكة ويجعل الواجهة تستجيب فورًا، ثم تعرض حالة المهمة بدل تجميد الشاشة.
