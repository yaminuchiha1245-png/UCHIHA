# UCHIHA Builder Security Notes

هذا الملف يصف الحدود الأمنية الملزمة للنسخة الحالية من Builder. لا يعد بديلًا عن تدقيق أمني مستقل قبل Production.

## العزل متعدد المتاجر

- يجب أن تحتوي كل Query خاصة بمتجر على `tenant_id` و`store_id`.
- جلسات عملاء المتاجر تستخدم Cookie مشتقة من Store ID، فلا تستبدل جلسة متجر جلسة متجر آخر.
- PostgreSQL RLS طبقة دفاع إضافية، وليست بديلًا عن شروط العزل داخل التطبيق.
- لا تعيد واجهات أصحاب المتاجر اسم المزود الحقيقي أو بيانات اعتماده أو الاستجابة الخام.

## العمليات المالية

- لا يضاف أو يخصم رصيد خارج Database Transaction.
- تقفل المحفظة وطلبات الإيداع والمنتجات باستخدام `FOR UPDATE` قبل تغيير الرصيد أو المخزون.
- يسجل كل قبول إيداع أو شراء في `wallet_ledger` مع مرجع فريد.
- تستخدم طلبات الإيداع والشراء سجل Idempotency خاصًا بالعميل ونوع العملية.
- إعادة نفس المفتاح مع نفس المحتوى تعيد النتيجة السابقة، ومع محتوى مختلف ترفض العملية.
- تحديث المخزون يكتب القيمة المحسوبة بعد قفل الصف ويشترط بقاء القيمة السابقة دون تغيير.
- تسجل العمليات المالية في `audit_logs` وترسل أحداثًا إلى `outbox_events`.

## إثباتات التحويل

- الوضع الحالي يقبل PNG وJPEG وWEBP بحد أقصى 1.5 MB.
- يتحقق الخادم من MIME والتوقيع الثنائي للملف، وليس اسم الملف أو امتداده فقط.
- قبل استقبال بيانات حقيقية يجب نقل الإثباتات إلى Object Storage خاص مع روابط مؤقتة وفحص إضافي للملفات.

## الأسرار والبيئات

- يمنع حفظ Tokens أو كلمات المرور أو مفاتيح API داخل GitHub.
- يجب إنشاء `APP_ENCRYPTION_KEY` عشوائي مستقل لكل بيئة.
- يجب أن تكون Staging Service وPostgreSQL وDomain مستقلة عن متجر UCHIHA القديم.
- يبقى `DEMO_SEED=false` و`ALLOW_DEMO_BILLING=false` في Production.
- لا يفعل Telegram أو المزود أو الدفع الحقيقي قبل إضافة الأسرار كمتغيرات بيئية والموافقة على الاختبار الحي.

## التحقق قبل الدمج

```bash
npm ci
npm run check
npm test
npm audit --audit-level=high
```

يجب كذلك اختبار PostgreSQL حقيقية، وسياسات RLS بحساب غير مالك للجداول، ورفع الملفات، والـRate Limiting، والاستعادة من النسخة الاحتياطية قبل جعل PR جاهزة للدمج.
