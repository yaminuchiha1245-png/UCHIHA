# UCHIHA Unified Platform

هذا المستند يثبّت الحد الفاصل بين منصة UCHIHA الجديدة وأي نظام قديم، ويمنع
تحويل المشروع إلى مجموعة تطبيقات وقواعد بيانات منفصلة.

## المبدأ

كل القنوات تتصل بـBackend API واحد وقاعدة PostgreSQL مركزية:

```text
Web Builder ─┐
Owner App ───┼──> UCHIHA Backend API ───> PostgreSQL
Storefront ──┤             │
Store Bot ───┤             ├──> Workers / Outbox
Admin Bot ───┘             └──> Providers
```

لا يُسمح للموقع أو البوت أو تطبيق الهاتف بالاتصال بقاعدة البيانات مباشرة.
ويحمل كل سجل تشغيلي نطاق `tenant_id` و`store_id` عندما يكون تابعًا لمتجر.

## نموذج المشروع

- `platform_projects`: المشروع الذي يملكه المستخدم، وقد يكون متجرًا أو بوتًا أو
  تطبيقًا أو نظامًا أو حزمة مختلطة.
- `service_catalog`: الخدمات التي يمكن شراؤها أو إضافتها.
- `project_components`: المكونات الفعلية للمشروع وحالة تجهيز كل مكوّن.
- `project_events`: سجل زمني للأحداث المهمة من كل قناة.

مكونات المتجر الحالية:

- `store_website`
- `web_admin`
- `storefront_bot`
- `admin_bot`
- `android_app`
- `ios_app`

أما `custom_system` و`custom_service` فموجودتان في كتالوج المنصة كبنية للمنتجات
اللاحقة، من دون إظهار وظائف غير مكتملة للمستخدم.

## سياسة دمج منصة البوتات السابقة

لا تُنسخ قاعدة SQLite أو جلساتها أو أسرارها إلى التطبيق الجديد، ولا يربط أي
عميل جديد بها مباشرة. عند بدء عمل البوتات تُنقل القدرات واحدةً واحدة إلى:

1. API موثقة ومحددة الصلاحيات.
2. جداول PostgreSQL المعزولة.
3. Worker وOutbox للعمليات الخارجية القابلة لإعادة المحاولة.
4. Adapter لاستيعاب صيغة البيانات القديمة مؤقتًا عند الحاجة.

هذه السياسة تسمح باستخدام الموقع والبوتين وتطبيق المالك مع البيانات نفسها من
دون ازدواج المنتجات أو الطلبات أو الأرصدة.

## تطبيقات الهاتف

- يوجد تطبيق مالك UCHIHA واحد يدير جميع المشاريع، بدل إنشاء نسخة تطبيق منفصلة
  لكل متجر.
- المتاجر الموجهة للزبائن تبدأ كتطبيقات PWA سريعة وقابلة للتثبيت.
- Android وiOS مبنيان من مشروع Capacitor واحد داخل `mobile/`.
- ملف Android التجريبي يُبنى في GitHub Actions ويُرفع كـArtifact.
- إصدار iOS للمتجر يحتاج macOS وXcode وحساب Apple Developer وتوقيعًا صالحًا،
  كما يحتاج خصائص Native مفيدة قبل التقديم العام.

## ترتيب توسيع المنتج

القاعدة تدعم التوسع، لكن التنفيذ التشغيلي يبقى عموديًا:

1. المتاجر والمدفوعات والدعم وتجربة المالك.
2. بوت المتجر وبوت الإدارة على الـAPI نفسها.
3. تطبيق المالك وخصائص Push/Camera/Biometrics.
4. الأنظمة والتطبيقات والخدمات البرمجية القابلة للشراء.

لا يُعرض أي مكوّن على أنه جاهز قبل وجود API واختبارات عزل ومسار تشغيل حقيقي له.
